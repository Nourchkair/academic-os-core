# Academia OS desktop app and local MCP

Academia OS is packaged as a native macOS app with a bundled `academia` runtime. The app, CLI, and MCP server use the same local configuration and interfaces. The app does not upload academic files or maintain an Academia-hosted student database. Academic files remain in the folder the student selects; rebuildable indexes and workflow state remain in that folder's `.academia/` directory. Optional AI providers receive material only when the student submits a request to them.

## Local MCP interface for agents and assistant hosts

`academia mcp serve` exposes tools over standard input/output. Read tools provide workspace status, capabilities, courses, tasks, bounded agent context, attention items, individual Review records, Activity changes, Library metadata, exact Library previews, and processing status. Narrow write tools support host-confirmed import into an exact inbox, an executable-choice-validated Review decision, separate execution of an already-approved supported domain change, and create-only AI-generated course artifacts. Imports preserve the original and start local extraction when supported; artifact creation is create-only and source-validated. The MCP server cannot independently verify that a host showed a confirmation dialog, so compatible hosts must confirm the exact write and effect with the student. Review Activity records identify the MCP caller as `agent:mcp`. MCP does not access external accounts, control a browser, submit school work, message school users, authenticate, or read credentials.

The MCP server delegates through the same CLI/core used by the dashboard. It is not an AI model or an MCP client. Codex, Claude, or another compatible host supplies reasoning and may connect to additional MCP servers independently. The in-app assistant host that can coordinate external MCP servers is a separate product layer and is not implemented by this stdio server.

For a packaged macOS app installed at `/Applications/Academia OS.app`, Tauri places the architecture-specific CLI sidecar in the app bundle. To find its exact filename:

```sh
ls "/Applications/Academia OS.app/Contents/MacOS"/academia-*
```

For Codex, add the sidecar path it prints to `~/.codex/config.toml`:

```toml
[mcp_servers.academia]
command = "/Applications/Academia OS.app/Contents/MacOS/academia-aarch64-apple-darwin"
args = ["mcp", "serve"]
```

For Intel Macs, use the `academia-x86_64-apple-darwin` filename instead. Claude Code can register the same local stdio server:

```sh
claude mcp add --transport stdio academia -- \
  "/Applications/Academia OS.app/Contents/MacOS/academia-aarch64-apple-darwin" mcp serve
```

Replace `/Applications/Academia OS.app` if the student keeps the app elsewhere. The MCP process inherits the local profile configuration. The agent's own file and process permissions still apply. The import tool accepts only an exact target returned by `academia_import_targets`; it copies, never moves, and retains acquisition and processing records. Generated artifacts are new Markdown files in the recognized course AI-generated area. For other academic-state changes, use the existing Review and Study contracts.

## Building and updating the macOS app

The desktop bundle contains the React/Tauri shell plus a PyInstaller-built, architecture-matched `academia` sidecar. It does not require students to install Python, Node.js, or a separate CLI. The sidecar carries the workspace template and runtime files needed for first-time workspace setup. Tauri creates a DMG and a separately signed update artifact; the GitHub release contains app binaries and updater metadata only. The app uses an Academia-specific self-signed code-signing identity for continuity across beta updates. It is not Apple Developer ID signed or notarized, so macOS may block the first launch until the user approves it in Privacy & Security.

Before the first release, configure these GitHub values:

- Repository variable `TAURI_UPDATER_PUBLIC_KEY` (recommended), or a repository secret with that name for compatibility: the complete public key generated by `npm run tauri signer generate -- -w ~/.tauri/academia.key`. The release workflow accepts either location.
- Secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: the matching Tauri updater private key and its password. Keep the private key outside the repository and retain a secure backup; losing it prevents future in-app updates for existing installs.
- Secrets `ACADEMIA_BETA_SIGNING_P12_B64` and `ACADEMIA_BETA_SIGNING_P12_PASSWORD`: the base64-encoded PKCS#12 and export password for a dedicated, self-signed code-signing identity named `Academia OS Beta Release Signing`. In Keychain Access, choose **Keychain Access → Certificate Assistant → Create a Certificate…**, use that exact name, set **Identity Type** to **Self Signed Root** and **Certificate Type** to **Code Signing**, and save it to the login keychain. In **My Certificates**, export the certificate together with its private key as a password-protected `.p12`, then base64-encode it with `openssl base64 -A -in Academia-Beta.p12`. Add the output and password as GitHub Actions secrets. Keep a secure backup of the `.p12` and password; losing this identity means future builds use a different code signer. Do not reuse Sawti's certificate or put the `.p12`, its private key, or either updater private key in the repository. Apple explains that self-signed certificates can be created in Keychain Access; they do not carry a certificate authority's trust ([Apple Keychain Access guide](https://support.apple.com/guide/keychain-access/create-self-signed-certificates-kyca8916/mac)).

The Academia code-signing identity and Tauri updater key serve different purposes: the former gives repeated app builds the same local code identity, while Tauri's updater key authenticates downloaded update artifacts. The release workflow imports the code-signing identity into a temporary runner keychain, signs the app, and deletes that keychain after packaging. It does not use Apple ID, Apple Developer ID, provisioning-profile, or notarization credentials. Tauri documents `APPLE_SIGNING_IDENTITY` as the macOS signing identity selector and the updater key as its own update-signature mechanism ([macOS signing](https://v2.tauri.app/distribute/sign/macos/), [updater](https://v2.tauri.app/plugin/updater/)).

The release workflow runs on a `v*` tag or manual dispatch, builds separate Apple Silicon and Intel DMGs, and leaves the GitHub release as a draft for review. To publish a version, update all version metadata, create and push its matching `v` tag, review the generated artifacts and release notes, then publish the draft. Students check for signed updates in Settings. Signature verification is mandatory; updater checks use HTTPS. The first direct install may require **System Settings → Privacy & Security → Open Anyway** after the user tries to open the app. Later updates are authenticated by Tauri's updater signature and use the persistent Academia code-signing identity. This route does not remove Gatekeeper's first-install warning.

For local development, install the optional bundle dependency with `python -m pip install -e '.[desktop-build]'`, then run `cd frontend && npm install && npm run tauri build`. The normal Vite development server does not build a sidecar; the desktop development bridge can still use an installed `academia` CLI.

## Privacy boundary

The update service sees a request for public release metadata and downloads signed application files. It does not receive a profile, course list, workspace path, source text, chat history, or academic records. MCP uses local stdio between the authorized host and bundled CLI. It has no listening network server or telemetry channel.
